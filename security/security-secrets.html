Manipuler les secrets sans les exposer

Identifiez les valeurs sensibles et organisez leur changement sans les copier dans la documentation.

Reconnaître un secret

Un mot de passe, un jeton d’accès, une clé privée, un secret de signature ou un code de récupération peut permettre une action ou un accès. Une valeur destinée à être publique dans un client ne doit pas être confondue avec une clé de service privilégiée ; en cas de doute, faites vérifier sa nature avant de la publier.

Où ne pas les placer

Ne mettez pas de secret dans le dépôt, le code envoyé au navigateur, un forum, une capture, une note publique ou un exemple de configuration. Utilisez les mécanismes sécurisés prévus par l’outil et l’organisation, avec un accès limité aux personnes nécessaires.

Un fichier ignoré par Git peut néanmoins être envoyé dans une archive : vérifiez aussi les exports et les pièces jointes.

Avant une intégration

  1. Identifiez le service et les permissions réellement nécessaires.
  2. Vérifiez le mécanisme de stockage autorisé.
  3. Utilisez des valeurs factices explicites dans la documentation.
  4. Contrôlez les journaux et messages d’erreur pour éviter un affichage involontaire.
  5. Documentez les dépendances sans recopier la valeur secrète.

Si un secret est exposé

Signalez rapidement l’exposition par un canal privé. La personne habilitée doit organiser la révocation ou le remplacement de la valeur et vérifier les intégrations dépendantes. Supprimer le texte visible ne suffit pas à établir qu’il n’a pas été copié.

Ne lancez pas une rotation générale de secrets sans comprendre l’impact : cela peut interrompre des services sans traiter le secret réellement concerné.

Conserver une trace utile

Documentez le type de secret, le service, la décision et les contrôles effectués, pas la valeur. Les échanges de récupération et les preuves sensibles restent dans les espaces autorisés. Consultez Incidents pour la coordination.
