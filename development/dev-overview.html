Préparer une modification de produit

Reliez le code, les tests et la documentation à un besoin vérifiable.

Référence pratiqueContenu relu · 26.09.2026
Pour qui ?Intervenants autorisés sur les supports Squared

Comprendre avant de modifier

Identifiez le comportement actuel, le résultat attendu et la surface concernée. Consultez les consignes du dépôt et les changements récents pour éviter de réintroduire une correction déjà traitée. Une demande visuelle peut dépendre de permissions ou de données : ne la réduisez pas automatiquement à un changement de style.

Préparer le travail

  1. Retrouvez la version de départ et les fichiers responsables du comportement.
  2. Reproduisez le problème avec des données de test non sensibles.
  3. Définissez les cas de réussite, d’erreur et de permission insuffisante.
  4. Choisissez une modification limitée et un retour arrière compréhensible.
  5. Identifiez les articles ou textes d’interface à mettre à jour.

Réaliser et vérifier

Séparez la présentation, la logique et les échanges de données lorsque cela améliore la lisibilité. N’ajoutez pas une dépendance sans besoin précis. Utilisez des tests adaptés à l’impact et relisez le diff pour repérer les modifications non souhaitées.

Une compilation réussie n’est pas un test de connexion réelle. Un serveur qui répond ne prouve pas qu’un compte a le bon périmètre. Indiquez le niveau de preuve produit par chaque contrôle.

Définir « terminé »

Le scénario demandé fonctionne dans le contexte testé, les états proches ont été contrôlés, les restrictions sont respectées et la documentation correspond à la version livrée. Les points non vérifiés restent explicitement ouverts.

Livrer sans mélanger les sujets

Utilisez Git & branches, Tests & QA et Publication d’une version. Ne glissez pas une migration, un changement de droits ou une opération destructive dans une correction de contenu.
