Organiser les changements avec Git

Gardez une histoire lisible et préservez les corrections réalisées par les autres intervenants.

Référence pratiqueContenu relu · 26.09.2026
Pour qui ?Intervenants autorisés sur les supports Squared

Préparer une base connue

Avant de travailler, vérifiez la branche et la version de départ. Lisez les changements récents qui concernent votre sujet. Une copie locale ancienne peut contenir une structure différente de celle déjà publiée.

Les conventions détaillées du dépôt priment sur les exemples de ce guide. N’effectuez pas de réécriture d’historique partagée sans une décision explicite et comprise.

Travailler sur une intention cohérente

  1. Créez une branche dédiée lorsque la modification demande préparation ou validation.
  2. Limitez les fichiers au besoin identifié.
  3. Consultez le diff avant chaque commit.
  4. Utilisez un message qui décrit l’intention : correction de recherche, documentation des tâches ou traitement d’une erreur précise.
  5. Conservez les tests et les notes utiles avec le changement.

Les préfixes comme fix:, docs: ou feat: peuvent faciliter la lecture lorsqu’ils sont utilisés dans le dépôt ; ils ne remplacent pas un message explicite.

Préparer une revue

Expliquez le problème, la solution, les tests et les limites. Signalez les données, permissions ou dépendances affectées. Une liste de fichiers ne suffit pas à comprendre l’impact pour l’utilisateur.

Gérer un conflit

Relisez les deux intentions avant de résoudre un conflit. Ne choisissez pas automatiquement votre version et ne forcez pas la branche principale pour éviter une intégration. Refaites les tests concernés après la résolution.

Avant la fusion

Vérifiez que la branche cible n’a pas reçu de changement incompatible, que les contrôles requis sont terminés et que les fichiers sensibles n’ont pas été ajoutés. Gardez un retour arrière identifié. Consultez la publication d’une version : fusionner du code et vérifier le site publié sont deux étapes distinctes.
