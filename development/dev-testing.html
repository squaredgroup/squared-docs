Vérifier un changement et décrire ses limites

Produisez des preuves adaptées au risque sans confondre simulation et test réel.

Pour qui ?Intervenants autorisés sur les supports Squared

Définir ce qui doit être prouvé

Commencez par le scénario attendu et le problème initial. Ajoutez les cas proches : données absentes, permission insuffisante, réponse lente, erreur et retour d’une session expirée. Une correction peut fonctionner dans le cas nominal tout en dégradant ces situations.

Choisir les contrôles

Un test de règle isolée vérifie une logique précise. Un test d’intégration vérifie les échanges entre modules. Un test de parcours examine ce qu’une personne peut accomplir dans l’interface. Une vérification visuelle compare la présentation dans un contexte donné.

Aucun niveau ne remplace tous les autres. Une capture correcte ne prouve pas l’enregistrement d’une donnée ; une réponse HTTP ne prouve pas les permissions de tous les rôles.

Exécuter sans toucher aux vraies données

  1. Utilisez des données de démonstration et des comptes de test autorisés.
  2. Isolez ou simulez les services lorsqu’un test ne nécessite pas la production.
  3. Bloquez les écritures réelles non prévues : achat, invitation, message, suppression ou modification de rôle.
  4. Testez le scénario, les erreurs et les interactions concurrentes concernées.
  5. Conservez les résultats et les étapes de reproduction.

Mobile et accessibilité

Contrôlez les largeurs utiles, le clavier, le zoom, les textes longs et les thèmes. Vérifiez les fenêtres, les erreurs et les états vides, pas seulement l’accueil. Consultez la checklist d’accessibilité.

Rédiger le bilan

Indiquez la version, l’environnement, les scénarios réussis, les échecs et les limites. Écrivez « parcours testé avec un service simulé » lorsque c’est le cas. Un contrôle non réalisé doit rester nommé comme tel. Les tests en production entre comptes réels demandent un périmètre et des autorisations distincts.
